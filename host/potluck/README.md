# potluck-capture — M0 host tooling

Reads a Potluck M0 node's serial stream, decodes Potluck Frames, records them in
[ARCHITECTURE.md §7.6](../../ARCHITECTURE.md)'s capture format, and prints the PDR and delay
histogram that §13-M0's acceptance test asks for.

This is **M0 tooling**. The real bridge is `potluck-bridge` at M2 (§7.1), which tees binary frames
rather than reading a console. The capture format written here is the one that bridge will use, so a
capture taken tonight is still readable then.

## Why there are two frame decoders

`potluck/frame.py` is a second, independent implementation of the codec in
[`firmware/components/pot_frame`](../../firmware/components/pot_frame). That duplication is
deliberate. A single implementation can only be tested for self-consistency — encode, decode,
compare — and a header field silently swapped with its neighbour passes every time. Two
implementations written from §5 and checked against the *same* golden bytes actually test the
specification. §14 asks for the wire format to be "specified and versioned independently of the
implementation"; two agreeing implementations are the cheapest way to mean it.

The same reasoning covers `link_stats.py`: a node ships histogram *counts* with no edges, so the
host has to know the bucket edges, so they can drift. `test_records.py` recomputes the node's own
p50/p99 from its counts and fails if the two disagree.

## Install

Nothing is required to parse a saved log or a capture:

```bash
python -m potluck --file node1.log --once
```

Reading a live serial port needs pyserial:

```bash
pip install pyserial
```

ESP-IDF already installs pyserial into its own environment, so on a machine set up to build the
firmware you can use that Python instead of installing anything.

## Use

```bash
python -m potluck --list-ports
```

Live table, no recording:

```bash
python -m potluck --port COM7
```

The 24-hour soak — this is the M0 acceptance run:

```bash
python -m potluck --port COM7 --capture captures/node1.jsonl --interval 60
```

Ctrl-C prints the summary and exits 0. Interrupting a soak is how a soak ends, not a failure, and
the summary is the deliverable.

Re-analyse afterwards, with no board attached:

```bash
python -m potluck --replay captures/node1.jsonl
```

Decode every frame as it arrives (needs `CONFIG_POT_FRAME_TEE=y` in the firmware):

```bash
python -m potluck --port COM7 --show-frames --show-logs
```

Default baud is 921600, matching `firmware/sdkconfig.defaults`.

## What it will not print

- **No one-way delay.** The two nodes' clocks are not synchronised, and ESP-NOW's retry path is not
  symmetric — a frame can sit in up to 31 retransmissions in one direction and none in the other
  (§3). So the tool reports round-trip time, the local transmit-queue delay, and the remote
  turnaround the peer measured on *its own* clock, and never divides anything by two.
  `test_records.py` asserts the absence of such a field, against the firmware's real output.
- **No interpolated percentiles.** A node measures a 16-bucket histogram, so p50 and p99 are
  reported as the bucket interval containing them — `2.0-3.0 ms`, not `2.47 ms`.
- **No zero standing in for unknown.** An unmeasured PDR shows as `--` in the table and
  `unmeasured` in the summary. §13-M0 wants a measured figure, and a default of 100% is a
  fabricated one.

## Tests

```bash
python host/potluck/tests/test_frame.py
python host/potluck/tests/test_records.py
```

or with pytest, and `tools/run_all_tests.ps1` runs these together with the C++ suite.

`tests/fixtures/stats_sample.jsonl` is generated by the C++ test binary, so the Python side is
tested against exactly the bytes a board emits:

```bash
build/tests/pot_tests.exe --emit-fixtures host/potluck/tests/fixtures
```

Regenerate it whenever `stats_json.cpp` changes. If a test then fails, the serial format changed and
this tool needs updating to match — which is the point of having the fixture.
