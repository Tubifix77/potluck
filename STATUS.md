# Status: every milestone, as measured

The full ledger behind the README's [What works today](README.md#what-works-today): every milestone, what it
set out to prove, and what happened when it was tested -- including the caveats and what is still unproven.
New to Potluck? [GETTING-STARTED.md](GETTING-STARTED.md) is the place to begin; this page is for when you
want to know exactly how far each claim has been taken.

## The milestones

Work is organised as **falsifiable milestones, M0–M20, with five intermediate steps (M5.1, M6.1, M8.1, M8.2,
M13.1)** — 26 in all; every "M-number" in Potluck's documents is one of them. The intermediate steps were added
when the first applications built on Potluck asked for something the platform could not yet do. Each milestone has
an acceptance test that can fail and a kill criterion (both spelled out in [ARCHITECTURE.md](ARCHITECTURE.md)); a
milestone counts as *built* when the code exists, and *accepted* only when its test has passed. A caveat is a part
of the test that was run differently from how it was written (a reset standing in for a power cut, say); a *waived*
part was not run, by the maintainer's decision, and the evidence that stands in its place is given.

Where they stand at **release 1.0.0 (2026-10-16)**: 25 of the 26 accepted; M20 built but not accepted. The first
published release was v0.2.0, earlier the same day.

**The reference bench.** Every hardware measurement below comes from the maintainer's test cell: three
ESP32-S3-DevKitC-1 N16R8 boards called **A**, **B** and **C**, each on its own USB cable, with the PC's USB-serial
adapter wired to A -- so the PC reaches B and C through A, over the radio. B also runs the Wi-Fi extender app. The
three sat on a desk, were walked through a house, and were placed around a room. That is a test bench, not a size: a
cell holds up to 20 boards. The step-by-step record behind every row is the maintainer's decision log,
[M0-LOG.md](M0-LOG.md).

| milestone | in one line | state |
|---|---|---|
| **M0** — two boards, one heartbeat | the wire format; membership (who is in the cluster and alive); measured packet-delivery ratio and round-trip delay | **accepted, 2026-10-04.** A 24.5-hour *soak* (a long unattended measured run) on three ESP32-S3 boards: no gaps, no reboots, no node wrongly declared dead, **100 % of packets** delivered both ways on all six links, round trip **4–6 ms typical, 16–22 ms at the 99th percentile**, memory flat to the byte. Then the *kill criterion* (the test that could have sent the radio choice back to the drawing board): a distance sweep through a real two-storey house, up to about 16 m, through four walls, a floor and a fridge. The link held everywhere; the worst spot still delivered 99 % of packets with round trips under 42 ms. The radio choice stands |
| **M1** — one remote read | the namespace; typed, staleness-checked reads | **accepted on hardware, 2026-10-04.** The PC, cabled to one board, read another board's value across the radio: value, unit, age and class. Unplug that board and the read says `UNAVAILABLE` with no number at all; plug it back in and it recovers by itself. Getting there found three bugs no emulator could show, including a value's age being measured from when it arrived rather than from when it was measured |
| **M2** — host in the loop | `potctl` (the command-line tool, `python -m potluck.ctl`); recording sessions to a capture file and replaying them | **accepted**, first under emulation (a 13.7-minute session, 11,444 frames) and **on hardware, 2026-10-04**: a 10-minute session over the real serial cable, covering all three boards, was recorded as raw frames and replayed on its own into a namespace identical to the byte (checked by SHA-256, and a wrong checksum is refused). The first attempt crashed after 70 seconds on a real bug: the PC tool could write two messages to the cable at once |
| **M3** — deploy and detach | A/B module slots (two copies, so a bad deployment falls back by itself); signed deployment packages | **accepted on hardware, 2026-10-04.** A signed package sent once, to one board, reached all three: that board passed it on to the others over the radio. Every board changed behaviour (the status light's healthy colour -- since 2026-10-14 healthy is always green), and kept the new behaviour after the PC was unplugged and all three were power-cycled on a mains charger. Then a deliberately broken package: each board crashed three times on it and went back to the previous version by itself |
| **M4** — locality contract enforced | the rule that tight control loops stay pinned to the node wired to the hardware, rejected at build time otherwise; plus [CAN](https://en.wikipedia.org/wiki/CAN_bus), the automotive wired bus | **accepted (2026-10-05), with one caveat: no instrument outside the boards has recorded the arbitration.** The build-time half passes: a manifest that binds a tight loop to a sensor on another node is rejected with an error naming the actor, the resource and both nodes. On a two-board CAN bus, one board flooded at about 3,000 frames a second while the other sent a safety message every second: all 301 arrived in order, each left within 335–683 µs, and the safety sender never lost arbitration. The first run found the safety message waiting 2.5–5.5 ms behind its own board's traffic, so the transport now sends in priority order. The milestone asked for this on a scope; the bench has none, so the evidence is the CAN controllers' own counters. A logic-analyzer trace would close that gap |
| **M5** — signed everything | a cluster certificate authority, node enrolment, authenticated frames | **accepted on three boards (2026-10-07).** Each board makes its own key and is enrolled over its own USB cable; an unenrolled board is refused and logged by the others. Every frame between enrolled boards carries a tag under a per-pair key, and a recorded command re-sent over the air is rejected. A safety message is signed, and one recorded before the whole cell restarts is still refused afterwards. Boards check deployment packages themselves and refuse unsigned ones, older ones, and ones signed outside the cluster. Signatures are [Ed25519](https://en.wikipedia.org/wiki/EdDSA), chosen because a board verifies one in 27 ms against 442 ms for the alternative |
| **M5.1** — sharing the radio | a node can be a Potluck member and a phone hotspot on a home Wi-Fi at once (asked for by the Wi-Fi extender app) | **accepted (2026-10-16), with its 24-hour run waived by the maintainer -- the longest run with the hotspot carrying traffic is 1.96 hours (no death, no reconnect).** All five parts built (2026-10-07). The cell follows a channel change and a lost node finds it again by scanning (about 5 s on the bench); a node can loosen or tighten its own death window while running without being declared dead; a node can declare itself busy; and a PSRAM build is measured (PSRAM copies at 11–31 MiB/s, ample for the extender). And a node out of range of the others joins through a single relay (a new design decision, ADR-009): reads, writes and death detection all work through it, still authenticated end to end, and a session captured through it replays byte-identical. And the real-world test: next to a working phone hotspot carrying a video stream, the cell declared no false death in 16 minutes; the stream costs round-trip jitter (worst 157 ms), not liveness (death window 600 ms). The 24-hour version was waived (2026-10-16): the bench could not be given over to a day-long run |
| **M6** — reconciler | failure-driven actor re-placement | **accepted on three boards (2026-10-08).** A "portable" actor -- one not tied to any board's hardware -- runs on one board and moves when that board dies: with its board held in reset, reads were answered by another board 0.46-0.69 s later, every time. When the dead board comes back, the actor is handed back without ever running in two places. Cut the cell in two and both halves run it; when the cut heals, the extra copy is stopped within half a second, and no reader ever accepts a value from the losing copy. Where an actor runs is worked out by every board independently from the same inputs ([rendezvous hashing](https://en.wikipedia.org/wiki/Rendezvous_hashing)), so there is no coordinator to lose. The boards now use their 8 MB of extra RAM ([PSRAM](https://en.wikipedia.org/wiki/Pseudostatic_RAM)) for buffers that are not time-critical |
| **M6.1** — the application owns the radio | the same node as one chip: a Potluck member, a station on a home Wi-Fi, and a phone hotspot at once (asked for by the Wi-Fi extender app) | **accepted on the bench (2026-10-08), with one caveat: the combined run lasted 14 minutes, not 24 hours.** One board is a cluster member, joined to a home Wi-Fi, and a phone hotspot at the same time, at the same speed as the hotspot alone (18-19 Mbps down); the cluster never mistook it for dead. When the router changed channel, the whole cluster followed it within about 3 seconds -- after a fix the test itself prompted. A later 1.96-hour combined run had no death and no reconnect; the 24-hour run, like M5.1's, was dropped by the maintainer (2026-10-16). Since then that board has also run the room-presence app's actors (M8.2), and running both found three faults in how a rebooting extender rejoins -- it sent the others to the channel it had saved, they followed each other while looking for it, and it took over work before its Wi-Fi had connected -- all fixed (2026-10-09). The radio stall it once showed after a cold start is the known limitation below the table |
| **M7** — [WebAssembly](https://webassembly.org/) tier | running **untrusted** code -- a third party's -- sandboxed, so it cannot take over the boards | **accepted on three boards (2026-10-11); off in a plain build, built into the release image.** It is for code the cell's owner does not fully trust; updates of the owner's own code are M11's, without an interpreter. **Measured as an experiment (2026-10-10) and left switched off:** a sandbox built on [wasm3](https://github.com/wasm3/wasm3) (a WebAssembly interpreter) stopped a program that loops forever, refused one that asked for a pin, and kept every program inside its own memory; it ran a real workload about 50× slower than built-in code, added 76 KB to the firmware, and did not disturb the board's cluster duties. With the option off the firmware is unchanged to the byte. **Accepted on 2026-10-11 as a feature:** a vendor's program -- signed by an author the owner certifies, wired up by the owner's package -- ran as a cluster workload on the boards, moved to another board with its saved state when its board was reset, and a program that never returns was stopped at every tick and then quarantined, with no board missing a heartbeat deadline. Boards built without the option refuse such packages. |
| *background compute* — on hardware it is **M9** (below) | a coordinator handing units of work to nodes that would otherwise sit idle, so a chip is not limited to watching one sensor. It is the answer to why an ESP32-S3 is worth clustering at all | **measured in simulation** (19 workers reach 18.99× the throughput of one, killing a worker mid-job loses no work) **and, since 2026-10-10, on hardware: three boards 3.41× faster than one** (M9). Listed here because it is the point of the project rather than a numbered step toward it |
| **M8** — host services | the agent (`python -m potluck.agent`), letting a PC offer services (say, speech-to-text) into the cluster's namespace | **accepted on the bench (2026-10-08).** A PC running the agent offers named services to the cluster -- only the ones its owner lists -- and a board calls one (the time of day, which a board cannot know by itself) every second. Pull the PC's cable and the board carries on: the value it last got is still readable, clearly marked as old and getting older, never passed off as fresh; plug it back and it picks up again by itself. |
| **M8.1** — attached hardware and the actor API | a real sensor's value in the namespace, read from another board with its age and quality; actors written against a documented interface instead of inside the firmware's main file (still compiled into the image) | **accepted (2026-10-16).** The chip's own temperature sensor on board B is read from the PC through board A: a value with its age, `FAULTY` with no number when the sensor fails, `UNAVAILABLE` when B is gone. Actors are now written against a documented interface, and the four existing ones were moved onto it. A fingertip on B's chip for a minute moved its value from 51.5 to 47.5 C, read through A, and it went back to 51.5 C after |
| **M8.2** — the room that knows it's occupied | three boards publish presence and motion from how a person in the room weakens their own heartbeat signals; no extra hardware (asked for by the room-presence app). The first application whose code lives in its own repository | **accepted (2026-10-16), with its 30 minutes of empty room and 24 hours with no PC waived by the maintainer -- no room on the bench could be kept empty for half an hour; the empty-room evidence is 3 hours of empty desk with no false alarm and 0 of 370 readings in the real room.** The experiment that could have stopped it passed (2026-10-10). Potluck now builds an application's own actors in from its own repository, hands them every received frame's signal strength and channel, moves its detector to another board when one dies and resumes it from a checkpoint, and shows its verdict on every status light without ever hiding a failing link. On the desk: 3 hours of empty desk with no false alarm once the detector was tuned, and seven board reboots with none. In a real room, boards placed around it: nobody there read empty (0 of 370 readings); a person walking, standing and sitting read present (100 %), and walking was told apart from standing still (99 % against 11 % "moving"). It senses the open room beyond the three boards, but patchily. Waived (2026-10-16): 30 minutes of empty room, and 24 hours with no PC |
| **M9** — borrowing an idle core | a board hands self-contained pieces of a job to neighbours with spare cores, and does a piece itself if a neighbour dies; the experiment that decides whether moving work between live boards is worth it | **accepted on three boards (2026-10-10), with no PC attached.** A job on one board -- an estimate of pi from a billion random points, in 960 pieces -- took 3 min 53 s on that board alone and 68 s with the other two lending their idle cores: **3.41x faster**, with the same answer to the last digit wherever each piece ran. Pressing reset on a lending board mid-job lost nothing: its pieces were run again. The lenders kept doing their own jobs as before. The board doing the work decides for itself, from its own measurements, whether lending a piece pays; a lender can say no. This reopened one of the design's closed decisions, as the experiment was set up to do, and only as far as the measurements reach |
| **M10** — the PC as a placement node | a PC runs cluster workloads while it is on, and the boards take them back when it is not | **accepted on the bench (2026-10-10); its caveat -- a cable "pulled" by stopping the PC's program -- closed on 2026-10-16 by a real pull: the boards took the PC's two jobs back 2-3 s after the adapter came out, and the PC took them again 2-3 s after it went back in.** The PC joins as a full member, from the boards' own code built for Windows and enrolled like a board, and reaches the boards it is not cabled to through the one it is. A job that prefers the PC moved there each time it joined -- handed over, never running in two places -- and back to a board within 0.63-0.69 s each time it vanished, five times in a row; with the PC on for 30 minutes it stayed put. Every board read the job's values from the PC |
| **M11** — firmware over the cell | a signed firmware update sent once, through one board, reaches every board over the radio, each trying it and rolling back by itself if it fails | **accepted on three boards (2026-10-10); its caveat -- no power cut by hand -- closed on 2026-10-16: B's cable pulled mid-receive left it on its old image, and pulled during its trial rolled it back.** Asked for by the room-presence app, whose boards on wall chargers around a room could not take a new command without being carried back to the PC. A signed image of ~0.85 MB reaches each board in about 1.5 minutes and the three-board cell in 5.4; each board tries it and keeps it only once it has rejoined the cell. An image that crashes, or never rejoins, rolls itself back on the first board and stops the update there; unsigned, foreign-signed, altered and older images are refused; no board dropped out of the cell during a transfer |
| **M12** — one command, any mix | Potluck as a platform: say which boards run which apps in one file, and one command builds, rolls out, deploys and checks it -- no variants, counters or order to know, and adding or removing an app without rebooting the boards, and a developer manual for people making apps | **accepted on three boards (2026-10-11); its caveat -- a reset, not a power cut -- closed on 2026-10-16: every plug out by hand; the first cut found a board that came back alone on a wrong channel (fixed), and on the fix the cell was whole in about 10 s and the guest resumed from its saved state.** Every board runs one image -- a board is a Wi-Fi extender because it holds Wi-Fi credentials, not because it was built as one. From plain Potluck, one `potluck.apply` put the room-presence app, the extender and a sandboxed guest on all three boards and checked every output: 390 s, most of it the firmware, two minutes a board. Taking the room-presence app off again took 23.5 s with no board rebooting and the guest's count carrying on; resetting every board at once, the guest resumed from its saved state. An apply that cannot work (a guest with a bad signature, too many actors, a missing board) changes nothing and says why; a board that was off gets the package from a neighbour. A reader with nothing but the public documents wrote, tested and deployed a new app in about 18 minutes |
| **M13** — the cell presents itself | a board on a home Wi-Fi presents every board's resources to Home Assistant and any MQTT tool, with no PC: a lightbulb on a board is switched from Home Assistant with the PC off | **accepted on the bench (2026-10-14), with caveats.** Home Assistant (on another machine on the network, with the Mosquitto MQTT broker) shows the cell's exposed resources as 3 devices and 4 entities and nothing else; its switch lights B's LED, each write announced; writes the package does not allow are refused; a dead board's entities go unavailable; two presenters fail over in 0.68-4.3 s, never both. The radio stall that met the kill line was AMPDU transmit aggregation on a board presenting over its own station: with it off, 13 h 19 min presenting and no stall, against twelve stalls with it on -- `apply` builds a presenting cell that way, at a cost to the extender's hotspot of about a quarter of its download and a third of its upload (12.2 / 10.4 Mbps against 16-18 / 16-17). TLS to the broker: 24.7 KB of internal heap on C, 34 KB with the MQTT client on the extender (low-water 114 KB). Caveats: the desk PC stayed on (power and consoles, no Potluck program in the path); the LED switched by hand in Home Assistant, not by an automation; boards reset rather than unplugged; the hotspot's cost from one speed test |
| **M13.1** — the cell answers a phone | no network and no PC (a boat, a field): a phone joins the nearest board's own Wi-Fi and sees which board is dead | **accepted on the bench (2026-10-14), with caveats.** Optional: the one place a board listens, read-only, behind a password the cell's owner sets. On A: joined with that password, the page showed all three boards; a board held in reset showed dead in about a second and alive again after its boot; every write or deploy request refused; a wrong password did not join; heartbeat loss 0.88 % with the page open against 0.61 % without; 15.3 KB of internal heap. Caveats: a laptop stood in for the phone, a reset for an unplug |
| **M14** — the hub | one program on the PC owns the link and holds the presentation of the whole cell; every tool becomes its client, several at once | **accepted on the bench (2026-10-14), with caveats.** `potluck.hub` holds the cable and serves one model; through it at once: M8's service, M10's placement host, a watch, a plan, live package changes. M10's handover through the hub 608-660 ms (M10: 629-687 ms, the kill line not fired); a second hub and a second `apply` refused by name; the hub killed and restarted with the cell untouched. The hub presenting in the cell's place (`present.hub`): the PC takes the role in 0.67-0.70 s and the boards take it back in 2.33-2.46 s, never two presenters, the same configs in Home Assistant. Eleven faults found and fixed on the way. Caveat: the PC switched off by killing its process |
| **M15** — telemetry over the cell | what a board prints to its console, available on the PC over the radio, at a rate the cell can carry | **accepted on the bench (2026-10-14), with caveats.** Health, links, actors and events over the radio in binary sections, pulled by the hub into the dashboard. Heartbeat loss 0.43 % with the hub pulling every 10 s, against 0.42 % without the pull and 0.66 % with no hub; RTT p50 unchanged, the slowest probe 60.2 ms (M0: none above 85 ms); 20 minutes with no console read, 0.57 % from the hub's own figures. A board that declared a long window shows asleep, not dead, and dead once the window runs out. `pot_sim` at 20 boards: airtime 26.0 % -> 28.8 %. Caveats: USB cables in for power; a declared window and a held reset stood in for a real sleep mode |
| **M16** — the dashboard | monitor everything that happens in Potluck, on a desk or a phone: is anything broken first, then the details | **accepted on the bench (2026-10-14), with one caveat: Home Assistant's Ingress not tested.** The first screen on the real cell, at phone and desk width; a phone on the home Wi-Fi opened it over HTTPS behind a login (a wrong password refused, then "All is well"); a look-only login cannot write and no deploy right exists; a recording of the last 24 h (about 0.5 MB an hour) replayed through the same tabs; ten dashboard streams cost the cell no more radio than one. Home Assistant's Ingress not testable here (the bench's Home Assistant runs in Docker, with no add-ons) |
| **M17** — Home Assistant, first-class | install it, and the cell's boards and resources are Home Assistant devices, read and controlled like any other | **accepted on the bench (2026-10-14), with one caveat: the maintainer's own Home Assistant, not a fresh installation.** In the maintainer's own Home Assistant (2026.10.1): HACS installed the integration from this repository, the hub was discovered with nothing typed (the cell's name and id), Add and Submit, Allow clicked on the PC, and the device Potluck hub (lab) appeared. In Home Assistant a device belongs to one config entry, so the boards stay the MQTT devices the cell's presenter creates and the hub adds to them over MQTT: state, RAM, uptime, signal, worst link, firmware (an update entity that installs nothing), a problem sensor per app -- 39 entities in all. An automation (an MQTT trigger) switched B's LED on: Home Assistant's write reached B and its LED actor counted the change. With the hub stopped (the PC "off"), the hub device and the diagnostics went unavailable within about 15 s and the boards' own values kept arriving every 2 s through C; started again, all 39 were back in 3-5 s. Two readers new to it followed the guide; the gaps the second found are fixed. Caveat: not a fresh installation |
| **M18** — the integration layer | any other system that can use the cell's resources gets an adapter, built on one interface; and your own programs use the same | **accepted on the bench (2026-10-14), with one caveat: Node-RED itself not installed.** INTEGRATIONS.md: the five duties, a program on the hub's API step by step, the MQTT payload for any consumer, a board module. A Node-RED integration built by a reader from the documents alone with no hub change (the kill line not hit), run against the real hub; a Node.js example program reads, watches and writes; each program has a share (a client pulling as fast as it could got its 20 requests a second, the dashboard stayed current, the cell saw no difference); integrations report their state and the dashboard lists them. A package reaches a cell with no cable through the boards in both (host-tested, 131 s). Two real cells in separate radio spaces on the bench, each reading the other's summary through their foremen. The setup wizard's survey of the bench proposes one cell, as it should for three boards that hear each other. Firmware reaches a cell with no cable the same way (shown on the bench: two boards the cable could not reach took a new image from the one it could, about 33 s each). A day in `pot_sim` (ten cells of ten): no death, no foreman handover, never a cell without its foreman |

**Known limitation, cause unknown: the radio stops accepting sends.** On a busy 2.4 GHz band a board's radio can
refuse every ESP-NOW send as `ESP_ERR_ESPNOW_NO_MEM` ("out of memory", `esp_now.h`) while it keeps receiving. It
was first seen on B after a power-on (2026-10-09): ~40 minutes of refused sends -- 6,131 refused, 1,133 failed, 354
completed -- until a reset ended it. It came back several times on 2026-10-16: on C twice during firmware rollouts,
and on A about 20 s after the PC's adapter was pulled. It is related to M13's presenting stall, which
was transmit aggregation (AMPDU) and is fixed by a build rule, but whether it has the same cause is untested. What
contains it now: a board whose every radio send has failed for 60 s restarts itself (`CONFIG_POT_TX_DEAD_RESTART_S`),
which the cell handles as a death and a return, and an `apply` caught by it stops cleanly and can be run again. A
related wedge -- a board's Wi-Fi task spinning on one core for hours -- is now ended by the task watchdog, which
resets a chip whose core has not run its idle task for 5 s (`CONFIG_ESP_TASK_WDT_PANIC`). Either way, why a board
last started is its `sys/reset` resource and the hub's `board.reset`.

Nothing above claims a measurement that was not made. Emulated runs stamp `"no_radio":1` on every
statistics line precisely so they can never be mistaken for a measured one; the hardware figures come
from runs stamped `"no_radio":0`. And the simulator earned some credit when the first soak ran — it had
predicted the round trip at 5.57 ms and the per-node frame rate at ~12/s from published figures alone,
and measured reality landed at 4–6 ms and 13.6/s.
