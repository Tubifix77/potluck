Potluck: the cell presented

The original idea -- Kubernetes for compute and attached hardware. Every board brings its sensors, cores and memory; the cell shares them, survives a board's death and presents them all as one machine, on the house network, by itself; an integration layer lets any program see them the way it usually sees resources. A PC is welcome, never required. M0 to M12 built the cell; M13 to M27 present it and bring the PC's side in. All are accepted on the test cell, many with caveats (STATUS.md has each one); M28 is planned. The picture began on 2026-10-11 as the draft for M13 on (BEYOND-M12.md). Updated 2026-10-27.

1 · The cell: n ESP32-S3 boards

123…n
⇄ ESP-NOW between them all ⇄

Every board brings

  • its cores, PSRAM and flash -- on the tested S3, 2 cores · 240 MHz · 8 MB PSRAM · 16 MB flash M21
  • its pins and what is wired to them: sensors, an LED, a buzzer M28
  • its radio: room presence, read from the links M8.2
Every board runs the same image. The owner's package says what runs where -- one line per app, changed in seconds M3 · M11 · M12.

The cell shares

  • values -- any board's readings, read from any board or from outside M1 · M2
  • cores -- lent to jobs that split into pieces M9 · M22; an app runs on one board
  • hardware -- a part on one board used from any board; its actor stays on that board M4 · M8.1
  • survival -- a portable app moves, with its checkpoint, when its board dies M6
Memory is not pooled: each board's RAM stays its own.

2 · The house network

Resource presentation M14 · M15

The whole cell, seen as one machine -- what Kubernetes' API server is to a cluster. One model, GET /api/model:

BoardsChipsLinksResourcesAppsModulesJobsServicesInputsFilesPinsUpdatesEvents

Every value with its unit, age and quality -- never a bare number. What is used, what is free, what runs where, what talks to what.

The PC's hub, when it runs optional

Cabled to any board, the hub holds the presentation and serves the dashboard, history and every program at once. With present.hub the PC presents the cell to MQTT too.

The cell itself, when it does not M13

Presenting is a role: a board on the house Wi-Fi takes it when the PC goes, and Home Assistant keeps switching a board's LED with no PC anywhere. Another board with Wi-Fi is the standby.

one API

3 · Integration layer

Adapters on the API M18

Five things every integration does (INTEGRATIONS.md):

  • names each resource in the other program's own terms, keeping the cell's ids
  • carries unit, age and quality: "unavailable", not a stale number
  • shows what the owner exposes, writes only what the owner allows, never deploys
  • is a module the owner chooses: off until turned on
  • reports its own state, so the dashboard shows it connected or not

A program on the hub's API costs the boards nothing; a board module (presenting is one) is for what must work with no PC.

With a PC, and without one

Without: a board on the house Wi-Fi connects out to the house's MQTT broker and presents the whole cell -- every board's LED and sensors -- to Home Assistant and any MQTT tool, read and controlled there. With: the PC's hub presents the same devices under the same names, plus the dashboard, history and your own programs. Either can come and go; Home Assistant sees the same LED throughout.

No network and no PC at all -- on a boat, in a field

The boards keep doing their jobs and helping each other; Potluck is just how they talk. When one high in the mast takes salt water and dies, the captain takes out a phone, joins the nearest board's own Wi-Fi with the owner's password, and sees which board is dead and since when M13.1. The page shows and never deploys. The owner can also let it switch things, behind a login, off by default M26. It is the one place a board listens, so it is optional, like every other module here.

Next: M28 -- sound across the cell planned

A built-in actor plays short patterns on a buzzer wired to its board. Any app's output chooses the pattern -- an alarm, say -- or a write from outside does; a room's alarm sounds in that room and nowhere else, with every PC off and a board unplugged. It needs a buzzer per board, chosen and checked before any code. A tone is a notice, never anyone's only smoke, fire or gas alarm. The test and its kill line are in ARCHITECTURE.md section 13.
One presentation, many viewers. Ten phones and three integrations cost the boards what one hub costs: the hub asks the cell once and serves them all.
Basic, or added by choice. Like the Wi-Fi extender app, the presenting module, phone access and every integration are optional -- some cells would find them a security liability, others filler they never use. They are off until the owner adds them, and the dashboard shows each as on, idle or not there.
The owner stays in charge. Only the owner's signed package changes what the boards do. Other programs read, and write only what the package allows.
